# Visual Workspace history, follow-up, and release hygiene design

작성: 2026-05-22 KST  
범위: Remaining-work Lane D, Lane E, Lane F only.

## Status summary

This document is a design and test-contract artifact. It does **not** claim the Visual Workspace is release-ready. Release-ready remains blocked until native live-click evidence passes, the current job native evidence manifest has `releaseProof=true`, and the final release matrix passes.

## Non-negotiable safety constraints

- No arbitrary shell UI bridge.
- No direct `finish`, `report`, recruit, broadcast, role-send, or task-edit UI bridge in this slice.
- No direct mutation of `.agent-work/07_JOBS/CURRENT.md` for history browsing or previous-job inspection.
- Generated evidence/output directories remain excluded from commits: `.agent-work/`, `.agentdock/`, `dist/`, `node_modules/`, `src-tauri/target/`, and `tsconfig.tsbuildinfo`.

## Lane D — Read-only history / inspector clarity

### Architecture decision

Choose a **snapshot payload extension** before adding a new `agentdock workspace history --json` command.

Rationale:

- The desktop app already has one read-only Tauri command, `workspace_snapshot`; keeping history under that controlled read path avoids opening a second bridge before the UI need is proven.
- A bounded history summary in the snapshot can be generated by reading `.agent-work/07_JOBS/JOB-*/README.md`, `TEAM.md`, `LIFECYCLE.md`, and `REPORTS/` metadata only.
- Previous-job selection can remain an inspect-only client state until a later approved slice needs full historical replay.

Rejected:

- `agentdock workspace history --json` as the first implementation step, because it would require documenting and eventually bridging another app-visible read command while the existing snapshot contract can carry the first useful history summary.
- Mutating `CURRENT.md` to inspect an older job, because it changes orchestration state and can confuse the active CEO job.

### Proposed snapshot fields

```json
{
  "history": {
    "mode": "read-only-summary",
    "active_job_id": "JOB-...",
    "jobs": [
      {
        "id": "JOB-...",
        "readme_path": ".agent-work/07_JOBS/JOB-.../README.md",
        "created_at": "best-effort timestamp or null",
        "selected_roles": 3,
        "reports": 2,
        "has_final_report": false,
        "is_active": true
      }
    ]
  }
}
```

### Inspector clarity contract

Role inspector copy should answer these questions in under 10 seconds:

- Is this role selected for the active job, bench-only, offline, blocked, or reported?
- What task card path and latest report path were observed?
- Is there a running pane id, or only configured role metadata?
- Is the preview source a live snapshot, stale last-good snapshot, demo fixture, or error fallback?

Do not render raw role objects or unrestricted report bodies in the first pass. Prefer path-only report evidence until redaction and truncation are independently tested.

### No-mutation test definition

The first implementation of historical summaries must add a regression that:

1. Creates a fixture project with at least two jobs and a known active `.agent-work/07_JOBS/CURRENT.md` hash.
2. Runs `agentdock workspace snapshot --json` with history enabled by default or a fixed flag.
3. Verifies the returned `history.active_job_id` matches the current job.
4. Verifies the previous job appears with `is_active=false`.
5. Re-hashes `CURRENT.md` and asserts it is byte-identical.

## Lane E — CEO follow-up controlled action

### Architecture decision

Use a dedicated CLI command: `agentdock job followup --message <text>`.

Rationale:

- The command can validate the active job, route only to the active job's CEO/orchestrator, and write a typed audit/event record.
- The UI/Tauri side can call a fixed argv builder and avoid exposing generic `send <role> <message>`.
- Follow-up keeps the CEO responsible for team changes instead of letting the UI directly mutate role tasks, send role instructions, broadcast, recruit, finish, or report.

Rejected:

- A fixed `send ceo-orchestrator <message>` bridge as the UI contract, because it couples the app to a role id and makes it easier to generalize into arbitrary role-send controls.
- Enabling selected broadcast, direct role send, recruit, finish, report, or task proposal in the same slice, because each needs separate validation, preview, audit, and native proof.

### Request DTO

```ts
interface CeoFollowupRequest {
  projectRoot: string;
  jobId: string;
  message: string;
  confirmToken: string;
}
```

Validation:

- `projectRoot` must resolve inside the selected project and contain `.agent-work/07_JOBS/CURRENT.md`.
- `jobId` must match the active job referenced by `CURRENT.md`.
- `message` must be non-empty after trimming and must respect a documented byte limit.
- `confirmToken` must be generated from the previewed request so submit cannot bypass preview.

### Result DTO

```ts
interface CeoFollowupResult {
  ok: boolean;
  jobId: string;
  deliveredTo: "ceo-orchestrator";
  inboxPath?: string;
  auditPath?: string;
  message: string;
  durationMs: number;
}
```

Result handling:

- Redact secrets in previews, results, errors, and audit rows.
- Use fixed argv only: `agentdock job followup --message <message>` plus fixed project/job flags if needed.
- Enforce timeout and failure copy that is actionable but not release-ready language.
- Audit request/result locally in the UI and in CLI output/artifacts when the CLI implementation lands.

### UI flow

1. Compose follow-up text.
2. Preview target: active job id and CEO/orchestrator only.
3. Confirm with explicit copy that this is a CEO follow-up, not role direct send.
4. Submit via fixed argv bridge.
5. Show result and append action audit event.
6. Refresh snapshot.

### Required future regression evidence

- Fake `agentdock` argv test proves no shell and exactly the follow-up command is invoked.
- Sandbox proof verifies the CEO inbox receives the message and no role inbox, task file, report, or `CURRENT.md` is mutated.
- Disabled-state tests cover no active job, stale snapshot, message empty/overlong, in-flight duplicate submit, and failed refresh.
